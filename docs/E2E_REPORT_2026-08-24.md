### Diseño — reutilizable después de cada deploy

`pickTargetMasa()` descubre dinámicamente una masa real `APROBADA`, no completada/cancelada/subdividida, prefiriendo la más "fresca" (fase más temprana) entre candidatas nuevas — así arriesga menos pisar trabajo real de otra persona que ya esté avanzada en staging. Una vez elegida, la fija en `tests/e2e/.state/masa-actual.json` (no versionado) para que reintentos y corridas por fase separada **retomen la misma masa**. Cada test de fase verifica el estado real de esa fase (y de la fase anterior) vía API antes de actuar, y se salta a sí mismo si no aplica — así la misma suite sirve tanto para un flujo nuevo de punta a punta como para reanudar uno interrumpido, sin tocar datos a mano.

La suite maneja automáticamente, liberando la masa fijada para la siguiente corrida, tres condiciones reales de staging que no son bugs pero sí bloquean el flujo de esa masa puntual:
- **Sin stock real de un ingrediente en SAP** (el checklist de Pesaje no puede completarse).
- **Masa `SUBDIVIDIDA`** tras confirmar Pesaje (el flujo real continúa en sub-masas hijas, no en la original — comportamiento de negocio legítimo).
- Fase ya `COMPLETADA` de una corrida anterior.

### Hallazgos de metodología (auto-detectados y corregidos durante la construcción)

Por transparencia, esta sección documenta problemas de la **suite misma** (no de la aplicación) que aparecieron mientras se la ponía a prueba contra datos reales y cambiantes de staging, y cómo se resolvieron:

1. **Preferir "la más avanzada" para reanudar trabajo era peligroso.** Una versión intermedia de `pickTargetMasa()` prefería continuar la masa más avanzada entre candidatas. En una corrida, eso hizo que la suite tomara por error una masa real (`MASA-OV-20260819-017`, id 1989) ajena a esta prueba. Esa fase (División) ya estaba completada, así que solo se hizo una lectura — sin escribir nada — pero el riesgo era real. Se corrigió: solo se retoma una masa ya iniciada por *esta misma suite* (vía archivo de fijación); entre masas nuevas siempre se prefiere la más fresca.
2. **`locator.isVisible({timeout})` no espera de verdad en Playwright** — a diferencia de `expect(locator).toBeVisible()`, es una comprobación inmediata del DOM; el `timeout` no reintenta. Varias comprobaciones condicionales (`si ya se inició esta fase...`) evaluaban antes de que React terminara de renderizar, dando falsos negativos. Se corrigió centralizando un helper `esperaVisible()` que sí usa `waitFor`.
3. **`BLOQUEADA` es el estado de reposo por defecto de *todas* las fases sin empezar**, incluida la próxima que sí está lista para trabajarse — no distingue "aún no le toca" de "ya se puede". La señal correcta es si la fase *inmediatamente anterior* quedó `COMPLETADA`; se corrigió así (`anteriorCompletada()`).

Estos tres puntos ya están resueltos en el código final; se documentan para que quede constancia de cómo se llegó a una suite confiable, no como hallazgos pendientes.

## 4. Hallazgos detallados (con evidencia)

### 4.1 Pesaje — el lote FEFO sugerido puede no tener stock real en SAP al momento de confirmar

**Punto del alcance:** (a) — validar que el checklist funcione con el flujo simplificado.

El checklist en sí funciona correctamente: un solo checkbox por ingrediente ("Registrar Pesaje") abre el formulario ya pre-llenado con el lote FEFO sugerido y el peso teórico, y "Guardar" lo confirma sin pasos adicionales — confirmado repetidas veces, en distintas masas, para conjuntos de hasta 14 ingredientes reales por masa (incluida AGUA, que no maneja lotes).

Sin embargo, al confirmar el pesaje completo (que dispara la salida de materia prima en SAP), la API respondió, de forma reproducible en más de una corrida:

```
POST /api/pesaje/2038/confirmar → 502 Bad Gateway
{
  "success": false,
  "message": "No se pudo registrar el consumo en SAP: 10001153 - Insufficient quantity for item MP0015 with batch 65361 in warehouse",
  "data": {
    "reintentable": true,
    "lote_fallido": {"item_code":"MP0015","batch":"65361","item_name":"AZUCAR"},
    "alternativas": [
      {"batch":"66904","cantidad_disponible":"74.915"},
      {"batch":"751","cantidad_disponible":"250.000"},
      {"batch":"ODV765","cantidad_disponible":"300.000"}
    ]
  }
}
```

El checklist ya había marcado AZÚCAR como "pesado" con el lote `65361` (el sugerido por FEFO), pero para el momento de confirmar, SAP ya no tenía stock suficiente en ese lote específico. La UI maneja este caso correctamente (mensaje con alternativas, opción de reintentar) — se recuperó seleccionando la alternativa `66904` desde la misma UI, exactamente como lo haría un operario, y la confirmación se completó con éxito en el segundo intento.

**No es un bug de la aplicación** — el mecanismo de recuperación existe y funciona — pero sí evidencia que el lote sugerido por FEFO puede desactualizarse entre el momento en que se pesa y el momento en que se confirma (más notorio en un ambiente de staging con datos compartidos/cambiantes). Vale la pena que el equipo evalúe si conviene revalidar disponibilidad justo antes de confirmar, no solo al abrir el formulario de pesaje.

También se observó, en otra masa, que un ingrediente (POOLISH) puede estar genuinamente **sin stock** en SAP — en ese caso el checkbox de "Registrar Pesaje" queda deshabilitado correctamente y el pesaje de esa masa no puede completarse hasta que haya stock; la suite lo detecta y libera la masa para la siguiente corrida en vez de fallar de forma confusa.

Evidencia: `tests/e2e/report/screenshots/03-pesaje-99-error-confirmar-intento1.png`, `tests/e2e/report/evidence/03-pesaje.json`.

### 4.2 División — BUG CONFIRMADO: el dato ingresado no sobrevive a una navegación fuera y de vuelta

**Punto del alcance:** (b) — al volver de Formado a División, ¿el dato ingresado sigue visible o vuelve a mostrar null?

**Confirmado: vuelve a mostrar "—" (vacío), no el valor guardado.**

Causa raíz (código real, `frontend/src/pages/Division/DivisionMasa.tsx`):

- `cantidadesDivididas` (unidades cortadas por producto) SÍ se rehidrata correctamente desde el backend en un `useEffect` que depende de `productos` (React Query).
- `formData` (máquina de corte, **temperatura de entrada**, reposo, **observaciones**) se inicializa vacío (`useState({...})`) y **no existe ningún `useEffect` que lo llene con lo que ya está guardado en backend**. Vive solo mientras el componente está montado; al desmontarlo (navegar a Formado) y remontarlo (volver a División), se pierde — incluso aunque la fase YA esté completada y el backend tenga el dato.
- La vista de histórico (cuando `fase_actual !== 'DIVISION'`) usa exactamente esas mismas variables `formData.*`, así que el problema también se ve al revisar una división ya completada días después, no solo en el momento de trabajarla.

**Evidencia — reproducido dos veces, de forma independiente:**

1. **Con datos controlados (masa `MASA-OV-20260820-021` / id 2038, conducida por esta suite):** se ingresó `Temperatura de Entrada = 24.7 °C` y una observación, se completó la división, se navegó a `/formado/2038` y de vuelta a `/division/2038`. Resultado: el campo "Temperatura de entrada" muestra `"—"` en vez de `"24.7 °C"`.
   - Captura: `03-division-01-formulario.png` (dato ingresado) → `03-division-bug-02-de-vuelta-en-division.png` (dato perdido, muestra claramente "MÁQUINA DE CORTE: Conic" junto a "TEMPERATURA DE ENTRADA: —")
   - Test: `expect(valorTemp).toHaveText(/24\.7/)` → **falla**, mensaje explícito: *"BUG: la temperatura de entrada debería mostrar '24.7 °C' (el valor guardado), no '—'"*

2. **De forma independiente, en una masa real de producción ajena a esta prueba** (`MASA-OV-20260819-017`, id 1989 — tipo GOLD, división completada por otra persona el 2026-08-19, verificación solo de lectura): mismo resultado exacto, `"—"` en vez del dato real.
   - Capturas: `evidencia-bug-division-masa1989-independiente-01.png` (en Formado) y `-02.png` (de vuelta en División, mostrando "—")

Esto confirma que el bug no depende de la masa ni de valores particulares — es sistemático.

### 4.3 Fermentación — la hora de entrada a cámara se muestra correctamente en horario Bogotá

**Punto del alcance:** (d) — ¿la hora de entrada se muestra en Bogotá (UTC-5) o en UTC?

**Correcto — se muestra en horario Bogotá, no en UTC crudo. Confirmado en 2 corridas independientes, con horas reales distintas.**

El código (`frontend/src/utils/timezone.ts`) usa `date.toLocaleTimeString('es-CO', { timeZone: 'America/Bogota', ... })` explícitamente para todo despliegue de horas — nunca se renderiza el valor crudo del backend sin conversión.

Prueba: se registró la entrada a cámara en el instante `T` (reloj real del runner) y se comparó el texto mostrado contra `T` formateado explícitamente en `America/Bogota`. Coincidieron exactamente en ambas corridas:
- Masa 2038: **"01:53 a. m."** (hora real UTC ~06:53).
- Masa 2048: **"02:34 a. m."** (hora real UTC ~07:34, ~40 minutos después, corrida independiente).

Capturas: `03-fermentacion-02-en-camara.png`.

**Nota de actualización de memoria del proyecto:** los campos `hora_salida_camara_sugerida` y `masa.requiere_camara_frio` mencionados en la memoria previa **ya no existen** en el código actual — Fermentación fue refactorizada (13-ago-2026) a un flujo por producto/línea donde cada línea entra/sale de cualquier cámara del catálogo (incluida una "fría") de forma independiente, sin distinguir cámara normal vs. cámara fría como flujos separados. Se recomienda actualizar esa memoria.

### 4.4 Empaque — confirmación visible y reflejo en el resumen

**Punto del alcance:** (e) — ¿aparece confirmación tras guardar? ¿lo guardado se refleja en el resumen?

**Ambas cosas funcionan correctamente.**

- Tras guardar la cantidad de paquetes de un producto, aparece un banner verde inline con el texto exacto **"Guardado correctamente"** (se autooculta a los 4s). Captura: `03-empaque-02-guardado.png`.
- Al completar el empaque, aparece un modal bloqueante **"✅ Empaque completado"** con los números de documento reales generados en SAP: `DocNum 239` (entrada de producto terminado) y `DocNum 505` (salida de materiales de empaque). Captura: `03-empaque-03-modal-resumen.png`.
- La vista "Resumen por variedad" lee de `GET /api/empaque/resumen-variedad?fecha=...` — un endpoint 100% independiente del estado local del formulario — y el test verificó programáticamente que el tipo de masa empacada (`ARABE`) aparece en esa respuesta tras completar el empaque. La aserción automatizada (`expect(JSON.stringify(resumen)).toContain('ARABE')`) **pasó**, confirmando que lo guardado se refleja correctamente en el resumen a nivel de datos.
  - Nota menor: la captura de pantalla de esa pestaña (`03-empaque-04-resumen-variedad.png`) no llegó a mostrar la pestaña correcta por un problema de navegación del propio test (no de la app) — la validación de datos ya mencionada es la evidencia que realmente prueba el punto.

### 4.5 Limitación conocida de la suite (no de la app) — Horneado con productos que no requieren horneado individual

Al correr el flujo sobre una tercera masa (`MASA-OV-20260820-031`, BATIDO_FRUTOS_ROJOS), el botón "Completar Horneado" quedó deshabilitado porque no todas las filas de la tabla "Unidades terminadas por producto" recibieron un valor. La causa más probable es que esa masa tiene una combinación de productos donde la lista que la suite usa para llenar filas (`productos` de `/masas/:id/productos`) no coincide 1:1 con las filas realmente renderizadas por Horneado para esa masa en particular (a diferencia de las otras 2 masas donde sí coincidió). No se investigó a fondo por límite de tiempo de esta sesión — se deja documentado como mejora pendiente de la suite, no como hallazgo de un bug de la aplicación (la UI se comportó consistentemente: no dejó completar con datos incompletos, que es el comportamiento correcto).

## 5. Otros hallazgos operativos (no pedidos explícitamente, mencionados por transparencia)

- **Rate limiting agresivo en la API de staging (no solo login):** durante esta sesión se recibió `429 RATE_LIMIT_EXCEEDED` varias veces por acumulación de llamadas de diagnóstico manuales (curl) + las propias corridas de Playwright en poco tiempo — en un caso sobre un endpoint normal (`GET /masas/:id`), no solo login. No bloqueó la suite en condiciones normales de uso (un run típico hace pocas decenas de llamadas), pero si este suite se integra a CI con corridas frecuentes o en paralelo, vale la pena que el equipo confirme los umbrales configurados para el rate limiter de staging.
- Ningún error de consola del navegador ni llamada de red con status fuera de 2xx durante Amasado, División (completar), Formado, Fermentación, Horneado ni Empaque en ninguna corrida — evidencia en `tests/e2e/report/evidence/*.json`.
- Se observó, en una masa real, que **Pesaje puede subdividir la masa** (`estado` pasa a `SUBDIVIDIDA`) — comportamiento de negocio legítimo, no un bug: el flujo continúa en sub-masas hijas independientes. La suite lo detecta y no lo trata como error.

## 6. Cómo correr la suite

```bash
cd frontend
npm install
# Definir credenciales de staging (nunca hardcodeadas en el repo):
export E2E_USERNAME=admin
export E2E_PASSWORD='********'
export E2E_BASE_URL=http://54.196.194.114   # opcional, es el default

npm run test:e2e                 # corre todo
npm run test:e2e:report          # abre el reporte HTML
npx playwright test tests/e2e/03-flujo-produccion.spec.ts   # solo el flujo completo
```

La primera vez que se corre sin una masa "fijada" (`tests/e2e/.state/masa-actual.json`), la suite descubre una masa real elegible automáticamente. Corridas posteriores retoman esa misma masa hasta que quede `COMPLETADA`, `CANCELADA` o `SUBDIVIDIDA` (o resulte inutilizable por falta real de stock), momento en el cual se descubre y fija una nueva.

## 7. Resumen ejecutivo

- **7 de 8 fases**: sin hallazgos de la aplicación, funcionan según lo esperado con datos reales de staging — confirmado de forma repetida en 3-4 masas distintas, no solo una.
- **1 bug confirmado con evidencia doble e independiente**: División pierde el dato ingresado (temperatura, observaciones) al navegar fuera y volver — tanto en la masa conducida por esta suite como en una masa real de otra persona. Causa raíz identificada en `DivisionMasa.tsx`: falta el `useEffect` de rehidratación que sí existe (correctamente) en `FormadoMasa.tsx`.
- **1 hallazgo operativo no bloqueante**: el lote FEFO sugerido en Pesaje puede quedar sin stock real en SAP al momento de confirmar; la UI ya tiene un mecanismo de recuperación funcional, usado con éxito durante las pruebas.
- Fermentación (horario Bogotá, confirmado dos veces) y Empaque (confirmación + resumen, con documentos SAP reales) se verificaron correctos con evidencia concreta.
- La suite quedó endurecida contra la variabilidad real de datos de staging (stock, subdivisión de masas, fases ya completadas) para poder reutilizarse después de cada deploy sin intervención manual.
